## Goal
Let the user run sprints onto several target branches of their own at once (e.g. feature branches that go to a pull request), many sprints per target branch, never merged into the main target such as develop; the user pushes and opens the pull request themselves; the product page shows each target branch and its sprints. Context: `roadmapa-dwmt.md` step K7 (scenario, model, git, end of work, page view, config scope), `bugs.txt` pts 2 and 3 in the dwmt-master plugin copy, sketch `.planning/sketches/006-miejsca-pracy` variant C (PD-6).

## Acceptance
- AC-1 A workplace is a stored product record: a target branch named by the user, the worktree dwmt uses for it, the base it started from, assigned sprints, state. The PO creates it and assigns sprints to it in conversation; a sprint names its workplace in its sprint file header (`workTree: <name>`); a sprint without it runs exactly as today. The branch belongs to the user: dwmt uses an existing branch as is; a branch that does not exist yet is created from the main tree's current branch, or from a base the user gives, without asking each time.
- AC-2 A workplace sprint runs on a temporary run branch as today and at its end squashes into the workplace target branch, one commit per sprint, each sprint on the result of the previous one; nothing is ever merged into develop, `git.target` or the main tree's branch; sprints of one target branch run one after another, different target branches may run in parallel under the supervisor.
- AC-3 The plan and review base of a workplace sprint is the workplace branch at the sprint start, so each review sees only that sprint's change, never the growing difference of the whole branch.
- AC-4 Roadmap, product directory and product commits stay in the main tree; the workplace branch gets only code commits; the roadmap marks a workplace sprint done when it is committed on its branch.
- AC-5 When all sprints of a workplace are done, dwmt shows "ready to push: branch <target branch>, N sprints" with the push command; it never pushes and removes the worktree only on an explicit request.
- AC-6 The product page shows workplaces as in sketch 006 variant C: a badge with the position on each workplace sprint card, a workplace switcher that filters the board and shows its git facts (branch, ahead/behind the base, pushed, uncommitted changes) and the push box; with no workplaces the page is exactly as today.
- AC-7 A test on a temporary repo: 3 sprints assigned to the user's branch `abc` give 3 commits on `abc`, develop and `git.target` do not change, the roadmap in the main tree shows them done, each review sees only its own sprint's change, and the generated page shows `abc` with three sprints.
- AC-8 Only the configuration this scenario needs is added; today's behaviour stays the default; the dwmt, product-layer and supervisor specs describe workplaces.

## Out of scope
- Page actions (assign, reorder, start/pause, push button): K10; the view only reserves their places.
- Other modes from `bugs.txt` pt 2 (work without a run branch on the current branch, profiles in setup).
- Numbering collisions with a roadmap kept on several branches (`bugs.txt` pt 6): K9.
- Tags on sprints and items.

## Decisions
- SD-1 Page view: sketch 006 variant C (PD-6, user, 2026-10-26).
- SD-2 Tests: only those related to the change, never the full `dwmt/test/*.test.mjs` suite during tasks.
- SD-3 If the architect finds this is two sprints, the second part is a separate sprint right after this one (page view second).
- SD-4 The user owns the target branches (they create and push them, dwmt never pushes); dwmt may create only temporary run branches and must squash each sprint into its target branch (user, 2026-10-26).
- SD-5 Base of a new target branch: the main tree's current branch by default, another base when the user names one; no question each time (user, 2026-10-26).
- SD-6 One squash commit per sprint on the target branch (user, 2026-10-26).
- SD-7 Sketch rules accepted: a done but unpushed workplace sprint sits in "Awaiting review"; uncommitted changes in the workplace tree hold its next sprint; "far behind" from 20 commits, configurable (user, 2026-10-26).

## Journey
- Run sprints on my branch: in the PO conversation "sprints X, Y on branch feature/platnosci" → the PO records the workplace (existing branch as is; a missing one from the current branch or a named base) and assigns X, Y → order as today → on the board X and Y carry the badge "platnosci · 1 z 2", "· 2 z 2".
- See what is ready to push: page → Roadmap tab → switcher under the tabs (Wszystkie / Główne drzewo / one entry per workplace with counts and ✓ / !) → pick the workplace → the board shows only its sprints, the facts strip (branch, ahead/behind its base, pushed, uncommitted) and, when all its sprints are done, the push box with the copyable command → the user pushes and opens the pull request outside dwmt.
- Notice a problem: "!" on a switcher entry (far behind its base, uncommitted changes holding the next sprint, a sprint waiting for UAT) → pick it → the strip says what and what to do.
- Entry points: board and sprint card kept (the card adds a workplace line); switcher and the "Wszystkie" facts strip added; nothing removed.
- Not applicable: no workplaces → no switcher, no badges, page exactly as today; a sprint without a workplace has no badge in any view.
